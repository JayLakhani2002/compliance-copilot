# ADR-0017 — Quality gate: committed cached embeddings + custom LLM-as-judge (amends ADR-0005)

**Status:** accepted 2026-08-24

## Context
Two gates were needed: (a) the retrieval eval (ADR-0013's golden set, hit@5/MRR) turned into a CI merge gate, and (b) an answer-quality gate scoring faithfulness/relevancy of the `retrieve -> answer` graph's real output (ADR-0014). Both need to run in CI without either depending on a live paid API on every PR or scoring against fake vectors — a gate that's "green" for the wrong reason (fake data, or silently skipped) is worse than no gate.

## Decisions

**(a) Committed cached embeddings, not a live API call, for the retrieval gate.** `evals/cache_embeddings.py` computes REAL `text-embedding-3-small` vectors for the 30 golden questions and every chunk the ingest pipeline produces from the two committed regulation snapshots (`evals/corpus_snapshot/*.xhtml`), and commits them as JSONL under `evals/embeddings_cache/{queries,corpus}.jsonl`. Format: one JSON object per line, `{"sha256": sha256(text), "model": ..., "dim": 1536, "vec": base64(float32 bytes via stdlib `array`)}` — keyed on `sha256(text)` (same idiom `pipeline.py`'s `Chunk.content_hash` already uses), so a changed question, changed corpus text, or changed embedding model changes the key. `src/compliance_copilot/cached_embeddings.py`'s `CachedEmbeddings(Embeddings)` raises `KeyError` (naming the cache file and the `make eval-cache` refresh command) on ANY miss — it never falls back to a live call or a fake vector. This means the CI `quality-gate` job runs hit@5/MRR on every PR, using genuine vectors, with zero `OPENAI_API_KEY` and zero network call.

**(b) A custom LLM-as-judge instead of Ragas 0.4.x**, amending ADR-0005's assumption. ADR-0005 and this task both assumed Ragas's `LangchainLLMWrapper`/`LangchainEmbeddingsWrapper` around `ChatOpenAI` — verified (Context7, `/vibrantlabsai/ragas`, `docs/howtos/migrations/migrate_from_v03_to_v04.md`) that both wrappers, and the classic `evaluate()` entry point, are deprecated in the installed-target 0.4.3 in favour of `llm_factory(...)`/raw `openai.AsyncOpenAI` clients — bypassing the `langchain_openai.ChatOpenAI` construction the rest of this app standardises on (ADR-0002's `make_llm()`). Ragas also pulls `numpy`, `datasets`, `pandas`, `pyarrow`, `pillow`, `networkx` and more — none of which this project otherwise depends on — for what amounts to 3 metric calls per question. The honest trade: Ragas ships more metrics (context precision/recall) that this project now doesn't get; in exchange, `evals/judge.py` is ~90 lines built entirely on the `ChatOpenAI(...).with_structured_output(JudgeVerdict, method="json_schema")` pattern the graph already uses (`graph/nodes.py`), fully understood, with no library API to re-verify every time Ragas migrates its own entry point again. ADR-0005 already named this custom-judge path as an acceptable fallback; this ADR promotes it from "supplement" to "the mechanism," for the reasons above.

**(c) Gates and thresholds.** `quality-gate` (hit@5 ≥ 0.93, MRR ≥ 0.80) runs on every PR — margin below ADR-0013's measured 1.000/0.881 so one ordinary golden-set addition doesn't fail a good PR. `answer-quality` (faithfulness ≥ 0.8; relevancy and citation-error-rate reported, not gated — relevancy is more phrasing-sensitive than the factual-grounding property this gate exists to guarantee) runs nightly (`schedule`, cron `0 3 * * *`), on `workflow_dispatch`, or on a PR carrying the `quality-gate` label — never on every push, since it needs a real `OPENAI_API_KEY` and costs real money.

**(d) Golden answers are human-written from the source text**, not LLM-generated: `evals/golden_answers.jsonl`'s 10 `reference` fields were written by querying the ingested `chunk` table for each anchor and reading the actual regulation text — a machine-written reference scored by a machine judge would let both inherit the same mistakes (lesson 10's stated reasoning).

**(e) Threshold at n=10 and judge bias — two honest caveats.** With 10 golden answers, one flaky judge verdict moves faithfulness by 0.1, so a 0.9 gate on a genuinely 0.9-quality system fails roughly one run in four; 0.8 is the gate until the set grows (growing n alone doesn't help at 0.9 — the gate must stay below the true quality by more than one question's worth). Second: the judge model is currently the same `gpt-4.1-mini` that writes the answers (ADR-0002 amendment), which is a self-evaluation bias risk — a model tends to rate its own phrasing as faithful. Mitigation already available: `make_llm()`'s Anthropic branch (`LLM_PROVIDER=anthropic`) gives a different-vendor judge the moment a key exists; until then the faithfulness number is a regression signal, not an absolute quality claim.

## Why not the others
- **Ragas** (`evaluate()` + collections API + `@experiment`): rejected per (b) above — the specific API surface ADR-0005 and this task assumed is mid-deprecation in the installed target version, and the dependency weight (`datasets`/`pandas`/`pyarrow`/`pillow`/`networkx`, none otherwise used) buys 3 metric calls' worth of value.
- **Live API calls in the retrieval gate** (no caching at all): rejected — every PR would need `OPENAI_API_KEY` in a public-repo-facing CI job, cost scales with PR volume rather than golden-set-change volume, and a rate-limited/flaky OpenAI call becomes a source of CI flakiness unrelated to the code under test.
- **Fake/random vectors for the retrieval gate** (e.g. `FakeEmbeddings`, already used in plumbing tests): rejected as the *gate* mechanism — a fake vector's nearest-neighbour ranking is unrelated to the real embedding model's, so a "green" gate would prove nothing about real retrieval quality. `FakeEmbeddings` stays exactly where it already is: fast, no-network plumbing tests that check code paths, not quality numbers.
- **Gating answer-quality on every PR**: rejected on cost/reliability grounds — an LLM-judge call is non-deterministic and non-free; gating a required check on it for every intermediate commit would either burn API spend fast or force the threshold so loose it stops meaning anything.

## Security & cost implications
- **Security:** the committed cache files and corpus snapshot are derived from/are public EU legal text (ADR-0012's reuse policy already covers this) — no PII, no secrets. `answer-quality`'s `OPENAI_API_KEY` lives as a GitHub Actions secret, never in the workflow file or logs (same pattern ADR-0016 already uses for `API_KEY`).
- **Cost:** `quality-gate` costs $0 in API spend (cached vectors only) on every PR. `answer-quality` costs ~$0.06–$0.10 for a 10-question run (gpt-4.1-mini, ADR-0002's verified $0.40/$1.60-per-MTok pricing) and only runs nightly/on-demand/labelled, not per-push. Repo size grows by the corpus snapshot (~2.1 MB) plus the embedding caches (~245 KB queries + ~4.6 MB corpus, base64 float32 JSONL) — a few MB, acceptable for a portfolio repo.

## How to reverse
`CachedEmbeddings` is a normal `Embeddings` implementation — deleting `EMBEDDINGS_PROVIDER=cached` from the CI job (and the cache files) reverts `get_embeddings()` to always returning `OpenAIEmbeddings`, no other code change. The custom judge (`evals/judge.py`) is plain LangChain/pydantic code with no library-specific API to unwind; swapping to Ragas (or DeepEval) later means replacing `judge()`'s body while `evals/golden_answers.jsonl` and `run_answer_eval.py`'s aggregation/gate logic stay the same — same reversibility property ADR-0005 already described for this exact swap.
