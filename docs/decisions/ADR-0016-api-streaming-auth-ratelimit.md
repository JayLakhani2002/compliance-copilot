# ADR-0016 — API streaming, auth, and rate-limit mechanics

**Status:** accepted 2026-08-24

## Context
ADR-0008 already decided the framework stack (FastAPI + Pydantic v2, SSE, API-key auth, `slowapi`). This ADR records the specific mechanics chosen when building `/ask` (`src/compliance_copilot/api.py`): how progress is streamed given `answer_node`'s structured (non-token) output, what streaming library (if any) is used, how the rate limiter is keyed and stored, and how auth failures are shaped — decisions concrete enough to need their own record, distinct from ADR-0008's framework-level choice.

## Options considered
1. **Per-node SSE progress events** (`event: node` after `retrieve`/`answer`, `event: final` with the validated `AnswerSchema`, `event: error` on failure) driven by `graph.astream(..., stream_mode="updates")`, vs. **token streaming** (`stream_mode="messages"`) on a free-text answer.
2. **Plain `StreamingResponse` + a 5-line SSE formatter** vs. **`sse-starlette`**'s `EventSourceResponse`.
3. **`slowapi`'s in-memory `Limiter`**, keyed on the caller's API key (falling back to remote address), enforced via **`SlowAPIMiddleware`** (real ASGI middleware) vs. the per-route **`@limiter.limit(...)` decorator**, vs. a Redis-backed store or a hand-rolled limiter.
4. **API-key header auth with `secrets.compare_digest`** vs. OAuth2/JWT.
5. **A `Content-Length`-checking ASGI middleware** for a request body size cap, vs. relying entirely on a future reverse proxy, vs. no cap at all.

## Decision
1. **Per-node progress events, not token streaming.** `answer_node` (nodes.py) uses `with_structured_output` — the model fills a Pydantic schema, not free prose, and every claim is citation-validated before it's accepted (ADR-0014). There is no safe partial token stream to forward: a half-emitted JSON object isn't valid `AnswerSchema`, and streaming raw tokens before validation would let an uncited or malformed claim reach the client ahead of the citation check that's the whole point of this system. Instead, `_stream_answer` (api.py) iterates `graph.astream({"question": ...}, context=..., stream_mode="updates")` and emits one `event: node` per graph step (`{"node": name, "articles": [...anchors], "recitals": [...anchors]}` for `retrieve`; `{"node": "answer", "attempt": n, "citation_error": bool}` for each `answer` attempt — the retry loop, ADR-0015, can run this node twice), then `event: final` with the validated `AnswerSchema` once `answer_node` succeeds.
   **How to reverse:** swap `stream_mode="updates"` for `stream_mode="messages"` on a redesigned free-text answer node — the SSE framing (`_sse()`) and the FastAPI route don't change, only what `_stream_answer` does with each streamed item.
2. **Plain `StreamingResponse`, not `sse-starlette`.** Verified against `sse-starlette`'s installed source (Context7 `/sysid/sse-starlette`): its `EventSourceResponse` only sets three headers and formats `event:`/`data:` frames — exactly what a 5-line `_sse()` helper plus Starlette's own `StreamingResponse` (already a transitive FastAPI dependency) does. This project's streaming need is one path (`retrieve -> answer`), no reconnection (`Last-Event-ID`), no multi-client fan-out — none of `sse-starlette`'s actual value-add over the bare primitive. Adding the dependency would be a name in `pyproject.toml` doing a job five lines already do.
3. **`slowapi`'s in-memory `Limiter`, keyed on the `X-API-Key` header (falling back to remote address when absent), enforced via `SlowAPIMiddleware`.** Every `/ask` call is a real LLM call (ADR-0002's cost model) — the rate limit's job is capping one caller's worst-case spend, so keying on the caller's identity (the API key) is more meaningful than keying on IP, which a caller can trivially move across. Falling back to remote address when no key is presented means an unauthenticated/wrong-key caller is still IP-throttled, not exempt from rate limiting entirely.
   **Round-1 amendment — middleware, not the `@limiter.limit(...)` decorator.** The original version decorated `/ask` with `@limiter.limit(lambda: settings.rate_limit)`. Round-1 review found (and confirmed by exploit — 30 rapid no-key requests, 30 rapid wrong-key requests, zero `429`s either time) that this never rate-limits a request that fails auth: verified in installed `slowapi/extension.py`'s `__limit_decorator`, the decorator's rate check runs *inside* the wrapped endpoint function, and verified in installed `fastapi/routing.py`'s `get_request_handler`, FastAPI only calls that wrapped function once `solve_dependencies()` succeeds — a `require_api_key` 401/403 raises straight out of dependency resolution, so the wrapped function (and its rate check) never runs. Fix: `Limiter(key_func=_rate_limit_key, default_limits=[lambda: settings.rate_limit])` + `app.add_middleware(SlowAPIMiddleware)`. `SlowAPIMiddleware` is real ASGI middleware (installed `slowapi/middleware.py`) — it runs for every non-exempt request *before* routing/`Depends` resolution, so the rate check happens regardless of whether auth later rejects the request. Verified in the same installed `middleware.py` (`_should_exempt`) that the decorator and the middleware are mutually exclusive: a route already carrying a `@limiter.limit(...)` decorator is skipped by the middleware ("there is a decorator for this route, we let the decorator handle it") — so this fix *removes* the decorator rather than adding the middleware alongside it. `/healthz` is exempted via `@limiter.exempt` (installed `Limiter.exempt`) — a liveness probe should never compete with real traffic for its own rate-limit budget.
   `settings.rate_limit` is still passed to `default_limits` as a callable (`lambda: settings.rate_limit`), not a bare string — verified against the installed `slowapi.wrappers.LimitGroup.__iter__`, a callable `limit_value` is re-evaluated on every request, a plain string is parsed once at decoration time. This is what makes the setting actually operator-adjustable at runtime (and testable — `tests/test_api.py`'s rate-limit tests lower `settings.rate_limit` mid-test and the very next request enforces it).
   **Ceiling, not a gap:** `Limiter()`'s default storage is in-process memory — correct for one process, meaningless across multiple replicas (each would have its own counter). `# ponytail:` comment at the `Limiter(...)` call site in api.py names this and the upgrade path (`storage_uri="redis://..."`, `slowapi`'s documented kwarg) for the day this API runs as more than one process.
4. **API-key header auth (`X-API-Key`), `secrets.compare_digest`, not OAuth2/JWT.** This is a single-tenant portfolio API with no user identity to federate and no third-party clients needing scoped tokens — a shared secret checked in constant time is the right amount of mechanism for "is this caller allowed to spend our LLM budget," not under-engineering. `settings.api_key is None` fails **closed** (503 "API_KEY not configured"), never silently open — an operator who forgets to set the env var gets a loud, safe failure, not an unauthenticated API.
5. **`BodySizeLimitMiddleware` (round-1 fix), a small `starlette.middleware.base.BaseHTTPMiddleware`.** Neither Starlette nor FastAPI caps request body size by default (verified: no such option in installed `starlette.applications.Starlette.__init__` or `fastapi.FastAPI.__init__` signatures) — confirmed by exploit in round 1: a 3 MB body was fully read and parsed before Pydantic's `max_length` ever rejected it. The middleware reads `Content-Length` (`settings.max_body_bytes`, default 16 KiB — generous headroom over `AskRequest.question`'s ~2000-char cap) and returns 413 *before* the body is read at all; a request that omits `Content-Length` while chunking a body (`Transfer-Encoding: chunked`) is rejected 411 rather than trusted. This is a stopgap, not the final word: `docs/ARCHITECTURE.md` §6 already designs a Caddy reverse-proxy boundary in front of this API, which will add a second, earlier cap once it exists in this repo — until then, this middleware is the only cap.

## Why not the others
- **Token streaming**: rejected because it's incompatible with citation validation running to completion before anything is accepted (ADR-0014) — node-level progress isn't the "watch it type" UX, because that UX can't coexist with "never ship an unvalidated claim."
- **`sse-starlette`**: rejected as unnecessary machinery for a single-path, no-reconnect stream — not a rejection of the library's quality, just this project's scope not needing what it adds over the bare primitive.
- **The `@limiter.limit(...)` decorator** (round-1 amendment): rejected — confirmed to never rate-limit a request that fails auth (see Decision §3's round-1 amendment above), which contradicts this API's actual security requirement ("unauthenticated traffic must still be throttled").
- **Redis-backed `slowapi` storage**: rejected for now as premature for a single-process deployment; the `ponytail:` comment marks exactly where to add it.
- **OAuth2/JWT**: rejected as more mechanism than a single shared-secret API needs today; revisit if/when this API gets multiple distinct client identities that need scoped, revocable, expiring credentials.
- **Relying entirely on a future reverse proxy for body size**: rejected as the only cap for *today* — no Dockerfile/Caddy config exists yet in this repo for the API to lean on, so "handled by the proxy" would currently mean "not handled at all." The middleware is the floor; the proxy adds a second cap later, it doesn't replace this one.

## Security & cost implications
- **Security:** the rate limiter (`SlowAPIMiddleware`) runs before routing/auth for every request; `require_api_key` runs before `_stream_answer`/the graph starts — both before an LLM call is possible (ADR-0008's boundary #1), and, after the round-1 fix, in an order where a request that never authenticates is still throttled rather than exempt. `BodySizeLimitMiddleware` runs alongside the rate limiter, rejecting an oversized body via `Content-Length` before it's ever read into memory. Error bodies never echo the question: `AskRequest`'s 422 validation-error handler strips Pydantic's default `"input"` field (which would otherwise echo the raw question back in the response body); `CitationError`'s message is built only from citation/anchor data (state.py's own guarantee); any other exception returns a fixed `{"type": "internal_error"}` body with the real exception logged server-side only (`logger.exception`, no question text passed to it). Verified live: a real `openai.LengthFinishReasonError` (an unplanned failure hit during manual testing of this feature — `answer_node`'s `max_tokens` cap was exhausted by structured-output overhead on a real question) correctly produced the generic `internal_error` SSE event with a full traceback in the server log and nothing leaked to the client.
- **Cost:** the per-key rate limit (`settings.rate_limit`, default `"20/minute"`), now actually enforced pre-auth too, directly bounds one caller's worst-case spend at ADR-0002's per-question cost × 20/minute — including an attacker who never presents a valid key. `get_llm_dependency`/`get_embeddings_dependency` are `lru_cache(maxsize=1)` — one client instance per process, not rebuilt per request. `settings.max_body_bytes` (16 KiB default) bounds worst-case memory per request regardless of auth outcome.

## How to reverse
The API layer is a thin wrapper — `_stream_answer` only calls `build_graph()`/`graph.astream(...)`, which have no FastAPI dependency (ADR-0008's own "how to reverse"). Swapping any one mechanic here (streaming shape, limiter backend, auth scheme) touches only `api.py`, never the graph/guardrail code underneath it.
