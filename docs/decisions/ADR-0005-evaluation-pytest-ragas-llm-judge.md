# ADR-0005: Evaluation — pytest-driven harness, Ragas metrics, custom LLM-as-judge, trajectory assertions, CI merge gate

## Status
Accepted. 2026-08-23.

## Context
Market research flags evaluation as **the differentiator, not agents/RAG themselves**: "evaluation" is named generically in 32% of ads, but specific tools (Ragas, DeepEval, LangSmith) are each named in under 5% — the practice of having eval discipline matters more than which library implements it, and the *choice* of tool is explicitly left to the project to justify. This project's stated goal is an eval-gated release pipeline: a PR that regresses answer quality should not be mergeable.

## Options considered
1. **pytest-driven harness** (pytest as the test runner and assertion framework) **+ Ragas** (RAG-specific metrics: faithfulness — does the answer only claim what the retrieved text supports; answer relevancy; context precision/recall) **+ a custom LLM-as-judge** (Haiku, ADR-0002, scoring against a written rubric) **+ trajectory assertions** (did the graph call the tools/nodes it should have, e.g. did `retrieve` actually get called before `answer`) **+ a golden dataset in-repo (JSONL)**, with thresholds enforced in GitHub Actions as a merge gate, results logged to **Langfuse datasets/scores** (ADR-0009) for trend visibility over time.
2. **LangSmith evals** (LangChain's own hosted eval product) — tightly integrated with LangChain/LangGraph, but it's a paid, US-hosted SaaS product, which is a weaker fit for this project's GDPR/EU-residency narrative than a self-hosted eval-results store.
3. **DeepEval-only** — a capable alternative eval library with LLM-judge and RAG metrics support; kept as an **optional** secondary tool rather than the primary one, since Ragas is more specifically RAG-metric-focused and the market research shows neither tool dominating naming frequency, so there's no strong market pull toward one over the other.
4. **promptfoo** — a prompt-level regression testing tool (good for "does this prompt still produce X given input Y"), but less agent-aware than what's needed here — it doesn't naturally express "did the agent call the right tools in the right order," which is a first-class requirement (trajectory assertions) for an agentic system, not just a prompt-testing one.

## Decision
**pytest** as the harness (tests are plain `test_*.py` files; fits the project's existing tooling, ADR-0011, and CI, ADR-0011). **Ragas** for the RAG-specific metrics: faithfulness, answer relevancy, context precision, context recall. A **custom LLM-as-judge** using Haiku (ADR-0002) against a written rubric, for qualities Ragas doesn't directly score (e.g., "does the answer correctly distinguish AI Act obligations from GDPR obligations when a question touches both"). **Trajectory assertions** — plain Python assertions over the LangGraph run's recorded node/tool-call sequence (not a separate library; LangGraph's checkpoint/state history already exposes this) — checking things like "the `retrieve` node was called at least once" or "the `critic` node ran before `guard_out`." A **golden Q&A dataset** committed to the repo as JSONL (human-reviewed question/expected-answer/expected-citation triples). Thresholds (e.g., minimum faithfulness score) are enforced in **GitHub Actions** as a required check on PRs into `develop`/`main` — a regression below threshold blocks merge. Results are also logged to **Langfuse datasets/scores** (ADR-0009) so score trends over time are visible outside of individual CI run logs.

**Verified API detail that changes how the harness is written:** Ragas (PyPI, version 0.4.3, verified 2026-08-23) has **deprecated** its classic `evaluate(dataset, metrics=[faithfulness, ...])` entry point (confirmed via Context7 against `vibrantlabsai/ragas`, source `src/ragas/evaluation.py`: the function body literally raises a `DeprecationWarning` pointing at `@experiment`) **in favor of** (a) a **collections-based API** for individual metrics — e.g. `from ragas.metrics.collections import Faithfulness`, constructed with an LLM via `ragas.llms.llm_factory(...)`, scored via `scorer.ascore(user_input=..., response=..., retrieved_contexts=...)` — and (b) an `@experiment` decorator for running metrics over a dataset. **The eval harness should be built against the collections API + `@experiment`, not the classic `evaluate()` function**, since building on a function the library itself flags as deprecated would mean rewriting the harness before this portfolio project is even finished.

## Why not the others
- **LangSmith evals**: rejected specifically for the EU/GDPR narrative reason stated above — a project whose whole premise is "we take EU data residency seriously" (`docs/ARCHITECTURE.md` §8) using a US-hosted SaaS for its eval results would be an inconsistency worth avoiding, on top of it being a paid product with less clear self-hosting story than Langfuse.
- **DeepEval-only**: not rejected outright — kept explicitly as an optional secondary tool for later comparison, since the market data gives no strong reason to pick one over the other and having both available is a reasonable stretch goal, not a core requirement.
- **promptfoo**: rejected because trajectory assertions (checking *which tools/nodes ran*, not just *what text came out*) are a named requirement for evaluating an agent, and promptfoo's model is fundamentally about prompt-in/text-out comparison.

## Security & cost implications
- **Security:** the golden dataset must not contain real user data (only synthetic/hand-written Q&A pairs) — since it's committed to the repo (a public portfolio repo, most likely), any accidental inclusion of real user questions would be a data leak. Eval runs that call Haiku (the LLM-judge) send golden-set questions/answers to Anthropic — same trust-boundary note as ADR-0002, though golden-set data is synthetic so the PII concern doesn't apply to *this* traffic the way it does to live user traffic.
- **Cost:** eval runs are bounded by golden-set size × PRs, not by user traffic (`docs/ARCHITECTURE.md` §9) — the main cost risk is running the *full* Ragas + LLM-judge suite on every single commit rather than only on PRs targeting `develop`/`main`; the CI workflow should be scoped accordingly to avoid burning GitHub Actions minutes and Anthropic API spend on every intermediate commit in a feature branch.

## How to reverse
The golden dataset (JSONL) and trajectory-assertion logic are not tied to Ragas specifically — swapping to DeepEval (or a different metrics library) means replacing the metric-computation calls inside the pytest test functions, while the dataset format, the pytest structure, and the CI gate mechanism stay the same. The LLM-as-judge is already custom code (a prompt + a Haiku call + a rubric), so it has no library dependency to reverse.
